# J1 Champion vs Challenger Contract

Date: 2026-05-08

Status: discovery contract accepted for future implementation. J2 core and J3 OOS stability implementations completed.

Source reviewed: `https://github.com/jlivanmaseda-maker/sqx-edge-pipeline.git`, commit `d4fddcc9a0eee10b42ddb7652a635a15d50b0e76`.

## Objective

Champion vs Challenger should become a native SQX Edge Pro decision workflow for comparing one validated Champion strategy against many Challenger candidates before promotion, rebuild, packaging or Strategy Builder handoff.

This phase does not add UI, runtime logic, backend endpoints or product claims. It defines the safe integration contract for the next implementation phase.

## Product Positioning

The feature should be presented as a controlled strategy comparison workflow, not as an automatic trading recommendation.

Preferred product labels:

- Champion vs Challenger
- Strategy Comparison
- Candidate Ranking
- Validation Board

Avoid restoring removed concepts as visible product surfaces:

- No `Top Picks` tab, block or headline.
- No `Matriz Completa` tab, heatmap tab or heatmap panel.
- No automatic "best strategy" wording without evidence and manual review.

## Integration Boundary

The Jose implementation is useful as product research, but should not be copied directly.

Native SQX Edge integration must follow the current architecture:

- Pure parsing and scoring logic first, without DOM access.
- Dedicated contracts before dashboard rendering.
- No direct `innerHTML` rendering of imported CSV values.
- No global monkey patches.
- No dependency on Jose dashboard element IDs or inline historical data shape.
- All imported strings rendered through existing escaping/formatting helpers.
- Thresholds and aliases declared in a maintained policy object or config, not scattered literals.

## User Flow

1. Operator imports or enters one Champion strategy.
2. Operator imports a Challenger CSV exported from StrategyQuant Databank or a compatible review file.
3. Optional: operator imports OOS block metrics.
4. SQX Edge validates schema, column aliases and numeric fields.
5. SQX Edge computes formal comparison, OOS stability and optional regime/EGT context.
6. Operator reviews ranked candidates, failure reasons and evidence.
7. Operator exports a redacted review summary or sends a candidate forward to a future Strategy Builder / handoff flow.

## Accepted Input Files

### Champion Input

Implemented in J2:

- One-row CSV.
- Manual form payload.
- JSON payload generated by SQX Edge.

Required normalized fields:

| Canonical field | Type | Required | Notes |
| --- | --- | --- | --- |
| `strategy_name` | string | yes | Escaped on render; never used as HTML. |
| `symbol` | string | yes | Must map to product asset universe when regime analysis is enabled. |
| `net_profit` | number | recommended | Used for context, not enough alone for promotion. |
| `profit_factor` | number | yes | Primary quality comparison. |
| `return_drawdown` | number | yes | Primary risk-adjusted comparison. |
| `drawdown_pct` | number | optional | Disabled by default for cross-run comparability unless matching assumptions are confirmed. |
| `trades` | integer | yes | Minimum sample-size guard. |
| `r_expectancy` | number | optional | Secondary quality context. |
| `stagnation` | number | optional | Secondary risk context. |
| `entry_indicators` | string | optional | Used for family detection after escaping. |
| `filters_result` | string | optional | May flag forward/OOS pass, but must not be treated as proof by itself. |

### Challenger Input

Implemented in J2:

- Multi-row CSV.
- JSON payload generated by SQX Edge.

Each row normalizes to the same canonical fields as Champion. Unknown columns are preserved in a `raw` metadata object for traceability but excluded from direct rendering until escaped.

### OOS Blocks Input

Supported in future J3/J4:

- CSV with one strategy row and repeated metric columns by block.
- Column pattern: `<metric> (OOS<n>)`, where `<n>` is a positive integer.

Preferred primary block metric order:

1. `CAGR/Max DD`
2. `Profit Factor`
3. `Net Profit`

Optional supporting block metrics:

- `Worst Year Profit`
- `Drawdown %`
- `Trades`

## Column Alias Policy

J2 implements a deterministic alias map. Minimum aliases:

| Canonical field | Accepted aliases |
| --- | --- |
| `strategy_name` | `Strategy Name`, `Strategy`, `Name` |
| `symbol` | `Symbol`, `Market`, `Asset` |
| `net_profit` | `Net profit`, `Net Profit`, `NetProfit` |
| `profit_factor` | `Profit factor`, `Profit Factor`, `PF` |
| `return_drawdown` | `Return/Drawdown`, `Return / Drawdown`, `Ret/DD`, `CAGR/Max DD` |
| `drawdown_pct` | `Drawdown %`, `Max Drawdown %`, `DD %` |
| `trades` | `# trades`, `Trades`, `Number of trades` |
| `r_expectancy` | `R Expectancy`, `Expectancy`, `R-Expectancy` |
| `stagnation` | `Stagnation`, `Stagnation %`, `Max Stagnation` |
| `entry_indicators` | `Entry indicators`, `Entry Indicators`, `Indicators` |
| `filters_result` | `Filters Result`, `Forward`, `OOS Result` |

Alias matching must be case-insensitive, trim surrounding whitespace and normalize repeated spaces. Ambiguous duplicate aliases should produce a schema warning.

## Parsing Rules

J2 parser requirements implemented:

- Accept comma and semicolon delimiters.
- Support quoted values and delimiters inside quotes.
- Preserve original row number for every parsed strategy.
- Reject files with no header.
- Reject files above the configured size cap.
- Return warnings for unknown columns, missing recommended fields and non-numeric metric cells.
- Return hard errors for missing required fields, empty strategy names or invalid Champion row count.
- Never execute formulas, links, HTML or script-like content from imported CSV cells.

## Scoring Contract

J2 computes a transparent comparison, not a black-box score.

Default formal checks:

| Check | Default rule | Severity |
| --- | --- | --- |
| Profit factor | `challenger.profit_factor >= champion.profit_factor * 1.05` | hard |
| Return/drawdown | `challenger.return_drawdown >= champion.return_drawdown * 0.95` | hard |
| Trades | `challenger.trades >= champion.trades * 0.70` | hard |
| Drawdown percent | disabled by default | advisory |
| Forward/OOS flag | enabled only when source field is present and configured | advisory |

The result object should expose:

- `formal_pass_count`
- `formal_fail_count`
- `advisory_pass_count`
- `advisory_fail_count`
- `failure_reasons`
- `warnings`
- `normalized_metrics`
- `source_trace`

## OOS Stability Contract

J3/J4 should compute block stability when OOS input is present:

- `block_count`
- `positive_block_count`
- `positive_block_ratio`
- `primary_metric_min`
- `primary_metric_max`
- `primary_metric_avg`
- `primary_metric_decay`
- `max_negative_streak`
- `has_negative_worst_year`

No OOS-derived label should be shown when fewer than the configured minimum block count is present.

## Regime / EGT Contract

J4 may add a regime/EGT layer after the core comparison is stable.

Required constraints:

- Use our maintained historical dataset access layer, not Jose-specific inline HTML assumptions.
- Map assets through our product universe.
- Keep thresholds configurable and documented.
- Label output as contextual evidence, not final truth.
- Block regime labels when data coverage is insufficient.

Candidate labels:

- `COMPLIANT`
- `RISK`
- `FLAT`
- `UNKNOWN`

## Security Rules

- Treat imported CSV/JSON as untrusted user input.
- Escape every imported string before rendering.
- Do not use imported names as DOM IDs without normalization.
- Do not persist raw imports automatically.
- Do not send imported strategy data to remote services.
- Do not include imported strategy files in portable ZIP builds unless explicitly selected by the operator.
- Keep buyer/customer/license material out of this feature.

## Test Plan

J2 added pure contracts before UI:

- CSV parser handles comma, semicolon, quotes and escaped quotes.
- Alias resolver maps accepted aliases case-insensitively.
- Required-field validation rejects incomplete Champion and Challenger inputs.
- Numeric parser handles `%`, decimal comma where safe, thousands separators and blank cells.
- XSS-like cells remain plain text after formatting.
- Formal scoring returns deterministic pass/fail reasons.
- OOS parser detects metric blocks and rejects inconsistent block numbering.

J3/J4 UI tests only become required when dashboard behavior changes:

- JS contracts for module API.
- Static load-order test if a new module is added.
- E2E screenshot if a new tab/panel appears.
- `git diff --check`.
